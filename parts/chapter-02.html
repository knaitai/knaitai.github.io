Chapter 2

Knowledge as a Computational Primitive

Chapter 1 argued that Knowledge Native AI puts knowledge to work at runtime. This chapter develops the first half of that idea: what it means to make knowledge itself a programmable computational primitive. The objective is not to force every form of knowledge into one representation, but to give a running system enough semantics to determine what is known, where it applies, how it may participate, and what computational expertise it can activate or shape.

2.1 From Stored Knowledge to Knowledge That Shapes Computation

Software systems already contain many forms of knowledge. Databases store assertions about entities and events. Knowledge graphs encode relationships. Type systems express constraints. Rule bases describe conditions and consequences. Configuration files capture operational policies. Learned models preserve statistical regularities acquired from data. Specialized models and algorithms embody knowledge about how particular classes of problems behave.

Yet the presence of knowledge does not guarantee its computational use.

A constraint may be recorded but never checked. A retrieved passage may be added to a prompt without affecting a result. A model may contain powerful predictive knowledge but never be invoked when that prediction is actually required. A formal specification may exist while a proposed action bypasses its verifier.

The distinction is between knowledge that is merely available and knowledge that participates in computation.

More precisely, a Knowledge Native program asks continuously: What is known now? What does that knowledge make relevant? What must be computed next? What expertise should perform that computation?

Stored knowledge answers: What is available?
Active knowledge answers: What computational role does it have now?

For knowledge to become active, a system may need to determine:

  • what the knowledge asserts, encodes, or provides;
  • where it came from;
  • when and where it applies;
  • what epistemic status it has;
  • what computation it can support, require, parameterize, constrain, or verify;
  • what computational expertise is associated with it;
  • and how resulting knowledge changes later computation.

Knowledge Native AI is therefore not simply a method for attaching more information to an LLM. It is an attempt to give knowledge an explicit and inspectable role in a heterogeneous computational system.

2.2 What Makes Something a Computational Primitive?

A computational primitive is a basic kind of object that a programming system knows how to represent and manipulate.

Numbers support arithmetic and comparison. Strings support concatenation, parsing, and search. Sets support membership, union, and intersection. Relations support selection, projection, and join. Tensors support numerical transformation, differentiation, and composition.

These primitives are useful not merely because they store values. They are useful because the programming system defines meaningful operations over them.

Primitive and operation are inseparable. A number without arithmetic is little more than a symbol. A relation without relational operations is only a table. A tensor without transformations is only an array.

The same principle applies to knowledge. If knowledge is to become a first-class computational primitive, a system must be able to identify it, inspect it, select it, test its applicability, combine it, challenge it, revise it, trace its consequences, and use it to determine what other computation should occur.

This last capability is especially important. Knowledge may participate directly through an operation such as support or constrain, but it may also participate by activating computational expertise: a planner, predictor, solver, simulator, verifier, LLM, database operation, ordinary algorithm, or human judgment.

This does not require every kind of knowledge to share one physical representation. A compiler invariant, clinical guideline, sensor observation, learned model, planning domain, and trajectory history are structurally different. The abstraction lies in their computational semantics, not in flattening them into a common storage format.

2.3 From Facts to Knowledge Objects

Consider the following assertion:

Package P depends on library L.

As ordinary data, this assertion might be stored as a row, an edge, or a field in a package manifest. That representation records the relationship, but it may not be sufficient for knowledge-aware computation.

A system may also need to know:

  • which version of P the dependency applies to;
  • which version range of L is required;
  • which manifest or build process asserted it;
  • whether the dependency is mandatory or optional;
  • when the assertion was last verified;
  • and which deployment or security conclusions depend upon it.

The bare fact records content. A knowledge object preserves content together with enough semantics for that knowledge to participate correctly in computation.

Definition 2.1 (Knowledge Object). A knowledge object is an identifiable computational unit that represents something known, proposed, observed, predicted, required, or assumed together with the provenance, scope, epistemic status, applicability, and operational semantics needed for its runtime use.

A knowledge object may be realized as a class, graph fragment, typed record, logical expression, database entity, model descriptor, structured message, or distributed resource. The definition concerns computational role rather than physical encoding.

A knowledge object may originate from a database, sensor, human expert, scientific publication, simulation, specialized model, or foundation model. Some knowledge objects are relatively static, such as guidelines and specifications. Others belong to the evolving runtime understanding, such as observations, hypotheses, predictions, plans, and verification results.

A minimal conceptual structure might be written as: 

KnowledgeObject
    identity
    content
    type
    provenance
    scope
    epistemic_status
    applicability
    computational_roles
    dependencies

This is not intended as a universal schema. It identifies categories of information that commonly determine how knowledge may participate in computation.

2.4 The Anatomy of a Knowledge Object

Identity

A knowledge object must be individually addressable. Identity allows a system to refer to a particular observation, rule, claim, prediction, specification, or judgment across multiple computational steps.

Without identity, it becomes difficult to preserve provenance, represent disagreement, revise an earlier assertion, or record that a later result depended upon it.

For example, observation:fever:child-17:2026-07-18T21:10 identifies one runtime observation. By contrast, guideline:respiratory-distress:retractions can identify general clinical knowledge whose applicability is evaluated against a particular patient only at runtime. General knowledge should not be duplicated or hard-coded for each subject.

Content

The content is what the object asserts, describes, predicts, constrains, specifies, or provides.

Content may take many forms:

  • a proposition about an entity;
  • an observed measurement;
  • a relationship between objects;
  • a constraint on allowable states;
  • a procedure or action model;
  • a probability distribution;
  • a model or model reference;
  • a formal specification;
  • or a prediction produced by statistical or neural computation.

Knowledge Native computation does not require content to be natural language. Symbolic expressions, numerical structures, executable procedures, graph patterns, learned parameters, and references to computational artifacts may all participate.

Type

The type identifies what kind of knowledge the object represents. Examples include:

  • observation;
  • claim;
  • definition;
  • constraint;
  • rule;
  • prediction;
  • procedure;
  • policy;
  • hypothesis;
  • model;
  • specification;
  • plan;
  • verification result;
  • or human judgment.

Type matters because different forms of knowledge admit different operations. An observation may update state. A constraint may eliminate a candidate. A hypothesis may accumulate support or challenge. A planning model may be consumed by a planner. A specification may be consumed by a verifier.

Provenance

Provenance records where the object came from and how it entered the system. Its source may be a database, document, sensor, model, human expert, external service, or previous derivation.

Provenance is more than citation. It may affect authority, trust, reproducibility, conflict resolution, and auditability. Two objects with identical content but different derivations are not necessarily computationally interchangeable.

A clinical hypothesis proposed by an LLM and the same hypothesis established by a diagnostic test may have identical text but very different epistemic status and permitted consequences.

Scope

Scope states where, when, and under which conditions the knowledge applies.

Scope may be temporal, geographic, organizational, legal, task-specific, population-specific, version-specific, operating-regime-specific, or tied to a model's validated domain.

Without explicit scope, systems tend to overgeneralize knowledge that is valid only under limited conditions.

Epistemic Status

A knowledge object also requires some account of how it should be treated.

It may be observed, asserted, inferred, predicted, assumed, disputed, verified, superseded, or invalidated.

Confidence may be one component of epistemic status, but it is not the whole of it. A high-confidence prediction remains a prediction. A formally verified property is different from a model's high-confidence judgment. An authoritative rule may have no probabilistic confidence score at all.

Applicability

Applicability captures the conditions under which knowledge may legitimately participate in the current computation.

A clinical guideline may apply to a particular age range and symptom pattern. A trajectory model may apply only to a particular vessel class, sampling regime, or operating region. A software invariant may apply only after initialization. A planning model may apply only when its state variables and action assumptions match the current problem.

Applicability is what turns potentially relevant knowledge into knowledge that may actually influence runtime computation.

Computational Roles

A knowledge object should expose or imply what role it may play. It may:

  • support or challenge a conclusion;
  • constrain a state, plan, or action;
  • satisfy or expose a requirement;
  • parameterize another computation;
  • activate computational expertise;
  • serve as input to an expert;
  • verify or invalidate a result;
  • revise prior understanding;
  • or contribute evidence to an explanation or authority decision.

This is the important departure from passive context. Knowledge can change what computation occurs and what consequences that computation is permitted to have.

2.5 Knowledge Objects and Computational Expertise

Knowledge and computational expertise are closely related, but they should not be collapsed into one abstraction.

Knowledge is what is known.
Computational expertise is a bounded capability for putting relevant knowledge to work for a particular computational purpose.

A trajectory history is knowledge; predicting the future trajectory is expertise. Actions, preconditions, effects, and goals are knowledge; searching them for a feasible plan is expertise. A formal specification is knowledge; establishing that a candidate satisfies it is verification expertise.

The distinction remains useful even when knowledge is embodied in a trained model. A trajectory transformer contains learned knowledge about motion patterns, while its computational expertise is the capability to map an appropriate trajectory history to a future-motion prediction. A foundation model contains enormous learned knowledge while providing broad expertise in interpretation, synthesis, reasoning, and generation.

A computational expert can therefore be described through an interface such as: 

ComputationalExpert
    identity
    capability
    scope
    requirements
    knowledge_inputs
    implementation_binding
    result_type
    authority

The implementation behind that interface might be an LLM, predictor, planner, rule engine, solver, simulator, optimizer, verifier, API, Python function, or human service.

This abstraction prevents KnaiTai from becoming tied to any one implementation technology. The Knowledge Runtime can reason about what expertise is required while existing execution infrastructure handles how that expert is actually invoked.

2.6 Knowledge Operations

Representing knowledge as an object is only half of the abstraction. A computational primitive becomes useful through the operations defined over it.

Definition 2.2 (Knowledge Operation). A knowledge operation is a typed computational action through which knowledge changes the system's knowledge state, evolving understanding, required computation, or permitted decision or action.

Some operations act directly on knowledge. Others connect knowledge to computational expertise.

Construct

Create a knowledge object from an observation, document, database record, rule, model output, computation result, or human assertion. Construction assigns the identity and contextual structure required for later use.

Retrieve

Locate knowledge potentially relevant to a task. Retrieval may be lexical, semantic, relational, graph-based, temporal, spatial, rule-driven, or programmatic.

Retrieval produces candidates. It does not establish applicability or authority.

Activate

Determine whether knowledge or computational expertise becomes eligible in the current state. Activation evaluates scope, prerequisites, current evidence, and other applicability conditions.

Activation can therefore occur at two related levels: a knowledge object may become active, and active knowledge may make particular computational expertise eligible or required.

Support

Increase the justification for a claim or hypothesis. Support may be logical, empirical, statistical, causal, or authority-based.

Challenge

Introduce knowledge that weakens, qualifies, or conflicts with a claim. A challenge need not prove the claim false. It may expose uncertainty, a missing assumption, or a competing explanation.

Constrain

Restrict permissible states, conclusions, plans, recommendations, or actions. A constraint may be evaluated directly or through specialized constraint-solving or verification expertise.

Transform

Convert knowledge from one representation into another while preserving identity and provenance where appropriate. Examples include entity grounding, normalization, feature construction, abstraction, and translation into the input representation expected by specialized expertise.

Derive

Produce new knowledge from existing knowledge through an identified computation. The derivation should retain links to its inputs and to the expert or operation that produced it.

Require

Declare that some evidence, state, or computation must exist before a later result may acquire a specified status or authority.

For example, a caregiver application may require respiratory status before a home-monitoring recommendation can be authorized. An autonomous system may require collision verification before a maneuver can execute.

Invoke

Request computational expertise whose applicability and requirements have been satisfied. The Knowledge Runtime need not implement the underlying scheduler, agent protocol, API transport, retry policy, or compute platform. Invocation is the semantic transition from this expertise is required to execute the bound capability.

Assimilate

Interpret a computational result in terms of what it establishes and incorporate that result into the evolving understanding.

A predictor's numerical output may become a prediction object. A planner's output may become a candidate plan with explicit assumptions. A verifier's result may establish that a property holds. An LLM interpretation may become a hypothesis rather than an accepted fact.

Reconcile

Resolve, prioritize, or explicitly preserve disagreement among knowledge objects and expert results. Reconciliation may use source authority, recency, scope, specificity, confidence, formal guarantees, or domain-specific precedence.

Revise

Modify the knowledge state when evidence, assumptions, or context change. Revision may update an object, supersede it, invalidate it, or propagate changed status to dependent conclusions and authority decisions.

Authorize

Determine whether accumulated knowledge and computational results satisfy the requirements for a recommendation, decision, or action to cross a defined authority boundary.

Authorization is not equivalent to confidence. It may depend on the participation of required expertise, satisfaction of constraints, completion of verification, provenance requirements, human approval, or other explicit conditions.

Explain

Expose the knowledge objects, expert invocations, results, and operations that contributed to a result. Explanation should be grounded in the computational trace rather than reconstructed solely as plausible prose.

Research Question. What is the smallest useful set of composable operations through which knowledge can activate and govern heterogeneous computation at runtime?

2.7 Relevance, Applicability, and Requirement

One of the most important distinctions in knowledge-aware computation is the difference among information that is related to a problem, knowledge that may legitimately participate, and knowledge or expertise that is actually required.

A retrieved document may discuss the correct topic but refer to an obsolete software version. A model may be generally relevant to trajectory prediction but invalid for the current sampling regime. A clinical guideline may apply to the patient but become computationally consequential only after a particular symptom is observed.

Definition 2.3 (Applicability). Knowledge or computational expertise is applicable when its scope, validity conditions, prerequisites, and status permit it to participate in the current computation.

Applicability may require checks such as:

  • Does it concern the correct entity or class of entities?
  • Is it valid at the relevant time?
  • Does it apply in the current environment, population, jurisdiction, version, or operating regime?
  • Are its prerequisites satisfied?
  • Are the expert's required inputs available?
  • Is its source or validation sufficient for the intended computational role?
  • Has it been superseded, contradicted, or invalidated?

But applicable does not necessarily mean required. Several experts may be capable of addressing a problem while only one is necessary. Conversely, governance knowledge may state that a particular verification is mandatory before authority can be granted.

Relevant means related.
Applicable means legitimately usable now.
Required means the computation cannot cross a specified authority boundary without it.

2.8 Presence Is Not Participation

Modern language-model and agent systems can assemble rich contexts containing user messages, retrieved passages, tool outputs, predictions, policies, and intermediate results. This is enormously useful. But placing information in a context window does not specify the computational role that information played.

Suppose a prompt contains:

  • a demand forecast;
  • a warehouse capacity limit;
  • a supplier delay notice;
  • and an analyst recommendation.

A language model may reason correctly over all four. But the surrounding application may still need to know that the forecast supported increased ordering, the capacity limit constrained the feasible quantity, the delay changed the plan, and an optimizer was required to compute the allocation. 

knowledge:
    demand_forecast_18
    warehouse_capacity_04
    supplier_delay_07

required_expertise:
    inventory_optimizer_03

expert_result:
    phased_order_plan_03

constrained_by:
    warehouse_capacity_04

authority:
    recommendation_allowed
Presence is not participation. Information appearing in a prompt is not evidence that it played a known computational role.

This is not an argument against prompting or LLM reasoning. Often the LLM will perform the relevant reasoning correctly. The architectural question is whether a consequential computational relationship must remain explicit, testable, revisable, or mandatory independently of the model's discretion.

2.9 A Minimal Knowledge Runtime

A minimal Knowledge Native program can now be understood as a runtime loop over knowledge, evolving understanding, and computational expertise. 

OBSERVATIONS / REQUEST / CURRENT STATE
                 ↓
          CONSTRUCT / UPDATE
              KNOWLEDGE
                 ↓
       WHAT IS APPLICABLE NOW?
                 ↓
       WHAT MUST BE ESTABLISHED?
                 ↓
     WHAT EXPERTISE IS REQUIRED?
                 ↓
       requirements satisfied?
          /              \
        no                yes
        ↓                  ↓
 expose/acquire       REQUEST INVOCATION
 missing knowledge         ↓
                    [existing workflow /
                     agent / tool layer]
                           ↓
                    EXPERT RESULT
                           ↓
                       ASSIMILATE
                           ↓
                  EVOLVING UNDERSTANDING
                           ↓
              support / challenge / constrain /
                revise / verify / require
                           ↓
                AUTHORITY CONDITIONS MET?
                    /              \
                  no                yes
                  ↓                  ↓
            continue runtime    recommend /
                                decide / act

The Knowledge Runtime does not need to own the mechanics of agent coordination, scheduling, queues, retries, model routing, or service invocation. Existing infrastructure can execute the requested computation.

Its responsibility is semantic:

  1. Represent knowledge and runtime state.
  2. Determine applicability of knowledge and expertise.
  3. Identify requirements created by the current understanding and intended decision or action.
  4. Activate expertise when its semantic conditions are met.
  5. Request invocation through an implementation binding or external orchestration layer.
  6. Assimilate what the result establishes into the evolving understanding.
  7. Revise affected knowledge and dependencies.
  8. Evaluate authority for recommendations, decisions, or actions.
  9. Preserve a trace of why each consequential computation occurred.

In simplified pseudocode: 

state = update_knowledge_state(
    observations,
    request
)

while not finished(state):

    active_knowledge = applicable_knowledge(state)

    requirements = determine_requirements(
        state,
        active_knowledge
    )

    experts = applicable_expertise(
        state,
        requirements
    )

    for expert in experts:

        if requirements_satisfied(expert, state):

            result = request_execution(
                expert,
                inputs=bind_inputs(expert, state)
            )

            state = assimilate(
                state,
                expert,
                result
            )

    state = apply_knowledge_operations(state)

    authority = evaluate_authority(state)

    if authority.allows_output():
        return emit(
            state,
            authority,
            trace=True
        )

    state = acquire_or_expose_missing_knowledge(state)

This pseudocode deliberately leaves execution infrastructure abstract. request_execution might call an ordinary Python function, LangGraph node, MCP tool, remote model service, planner, solver, ROS component, workflow engine, or human task.

The Knowledge Native abstraction is concerned with why that expertise became necessary, what knowledge it consumed, what its result established, and what changed as a consequence.

2.10 Knowledge, Expertise, and Orchestration

The distinction among these three concerns is important.

Knowledge represents what is known and the semantics of its use.
Computational expertise represents what specialized computation can establish.
Orchestration executes and coordinates the underlying components.

A multi-agent framework might decide how messages move among a medical agent, pharmacy agent, and critic agent. A workflow engine might schedule a predictor and retry it after failure. A model router might select among foundation models for cost or latency.

Those are useful capabilities, but they address a different problem.

The Knowledge Runtime asks why a pharmacy contraindication check is required, what evidence it needs, what its result establishes, and whether the treatment recommendation can proceed without it. The expert that performs the check could be an agent, rule engine, database query, or ordinary function.

Agents are therefore one possible delivery mechanism for computational expertise. They are not the Knowledge Native abstraction.

Similarly, KnaiTai need not become a universal expert router. Routing asks which available component should receive a request. Knowledge Native activation asks what the evolving state implies must be established and what kind of expertise has the semantics and authority to establish it.

2.11 Granularity and Composition

A practical issue is deciding what should count as one knowledge object.

A full policy or guideline may be too coarse because individual provisions have different scopes and effects. At the other extreme, treating every token, sentence, or graph edge as an independent object may obscure coherent meaning and make computation unwieldy.

A useful knowledge object usually satisfies three conditions:

  • Coherent applicability. Its conditions of use can be evaluated meaningfully as a unit.
  • Coherent computational role. The system can identify what the object may do or what expertise it may participate in.
  • Coherent provenance. Its source or derivation can be preserved without ambiguity.

Granularity may change during computation. A document may enter as one resource and then be decomposed into claims, constraints, definitions, or procedures. Several fine-grained objects may later be composed into a larger hypothesis, state estimate, plan, or explanation.

Definition 2.4 (Knowledge Composition). Knowledge composition is the construction of a larger knowledge object or understanding from smaller objects while preserving the identities, roles, dependencies, and provenance of the contributing parts.

Composition is important because intelligent computation moves across levels of abstraction. A system may reason over observations, intermediate hypotheses, predictions, constraints, plans, and aggregate conclusions within the same task.

2.12 Knowledge Objects Need Not Be True

The phrase knowledge object should not be interpreted as a guarantee of truth.

An intelligent system must represent uncertain observations, competing hypotheses, model predictions, disputed claims, expired policies, provisional plans, assumptions, and assertions later shown to be false.

What makes these objects suitable for knowledge-aware computation is not certainty. It is that their epistemic status and conditions of use are represented.

Knowledge Native AI does not require every knowledge object to be accepted as true. It requires the system to represent what kind of object it is, why it is available, and how it may legitimately be used.

This is especially important once specialized expertise participates. A predictor produces a prediction, not an observation. A planner produces a candidate plan, not proof of feasibility. An LLM may produce a hypothesis. A verifier may subsequently establish a stronger property about one of those results.

Preserving these distinctions prevents an evolving understanding from collapsing heterogeneous computational products into an undifferentiated collection of “facts.”

2.13 Knowledge Capsules

Individual knowledge objects are useful primitives, but practical systems often need a larger portable unit that packages related knowledge with its computational semantics.

A knowledge capsule can group knowledge, scope, applicability, requirements, expert bindings, outputs, authority semantics, and provenance without requiring the underlying computational implementation to live physically inside the capsule. 

KnowledgeCapsule
    identity
    knowledge
    scope
    applicability
    requirements
    expertise_binding
    result_semantics
    authority
    provenance

For example, a clinical capsule might contain general respiratory-distress knowledge and bind it to a pathway evaluator. A trajectory capsule might describe the scope and requirements of a trained predictor and bind to a model service. A verification capsule might package a specification and bind to a formal checker.

The capsule therefore provides a declarative boundary between what the runtime needs to know about a capability and how that capability is implemented and executed.

Later chapters develop this abstraction in greater detail.

Knowledge Native Thinking

When encountering a source of knowledge, ask not only what it contains, but what role it can play in a running computation.

A document is not yet an instruction. A graph edge is not automatically a constraint. A model is not automatically applicable. A prediction is not an observation. A planner's output is not automatically executable. A human note is not automatically authoritative.

Knowledge Native Question. What does this knowledge mean computationally: when does it apply, what can it establish or require, what expertise can put it to work, and what should change after that computation occurs?

Once that question is asked, the design problem changes. The objective is no longer merely to move information into a model or pipeline. It is to program the semantics through which knowledge activates computation and through which computational results become new knowledge in an evolving understanding.

Chapter Summary

  • Knowledge may exist in a system without participating explicitly in computation.
  • A computational primitive is defined both by representation and by meaningful operations.
  • Knowledge is intentionally broad: it may be declarative, situational, historical, structural, procedural, formal, learned, or human.
  • A knowledge object represents content together with computationally relevant identity, provenance, scope, epistemic status, applicability, roles, and dependencies.
  • General domain knowledge should remain distinct from runtime bindings to particular entities or situations.
  • Knowledge and computational expertise are related but distinct: knowledge is what is known; expertise is a bounded capability for putting relevant knowledge to work.
  • Computational experts may include LLMs, predictors, planners, rule engines, solvers, simulators, optimizers, verifiers, algorithms, services, and humans.
  • Knowledge operations include construction, retrieval, activation, support, challenge, constraint, transformation, derivation, requirement, invocation, assimilation, reconciliation, revision, authorization, and explanation.
  • Relevance, applicability, and requirement are distinct concepts.
  • Presence of information in an LLM context is not the same as known computational participation.
  • The Knowledge Runtime determines what knowledge and expertise are applicable, assimilates computational results, and evaluates authority as understanding evolves.
  • Existing workflow and multi-agent infrastructure can execute computations; KnaiTai need not replace it.
  • A knowledge capsule can provide a declarative unit connecting knowledge to applicability, expertise, result semantics, and authority.

Discussion Questions

  1. Which properties of a knowledge object appear universal, and which are necessarily domain-specific?
  2. How is a knowledge object different from a typed record containing metadata?
  3. When should a learned model itself be represented as knowledge, and when should it be represented as computational expertise?
  4. Can the same knowledge participate in more than one kind of computational expertise?
  5. What is the difference between an applicable expert and a required expert?
  6. Which knowledge operations belong in the runtime itself, and which should be delegated to specialized experts?
  7. How should an expert's result declare what it has actually established?
  8. What authority should be assigned to predictions, plans, LLM hypotheses, formal proofs, and human judgments?
  9. How should KnaiTai interoperate with an existing agent or workflow framework without duplicating orchestration?
  10. What is the appropriate boundary between an individual knowledge object and a knowledge capsule?

Exercise 2.3: Knowledge or Expertise?

Exercise 2.4: Separate Relevance, Applicability, and Requirement

Suppose a system has access to ten potentially relevant knowledge objects and four computational experts. Design a procedure that determines which knowledge is applicable and which expertise is merely available, applicable, or mandatory before a specified action may proceed.

Exercise 2.5: Specify an Expert Interface

Choose a predictor, planner, solver, simulator, verifier, or LLM capability. Specify its identity, capability, scope, requirements, knowledge inputs, implementation binding, result type, and authority.

Exercise 2.6: Trace a Runtime Cycle

Construct a short trace in which an observation activates general knowledge, that knowledge requires specialized expertise, the expert returns a result, and the result changes what may happen next. Identify each knowledge object and operation in the trace.

Exercise 2.7: Separate Semantics from Orchestration

Sketch a system that uses an LLM, one specialized expert, and one verifier. Mark which decisions belong to the Knowledge Runtime and which mechanics belong to an existing workflow or agent framework.

Exercise 2.8: Define an Authority Boundary
